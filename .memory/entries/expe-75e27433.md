Found while scoping stage 3 (Venice parity). A silent process kill at exactly the resolution the parity target needs.

SYMPTOM: solving multistory_building at 128x256 kills the interpreter with SIGSEGV (exit 139). No exception, no traceback, no partial output - the process simply dies. Threshold measured by bisection on grid size:
  64x128   16,576 dofs  OK
  96x192   37,152 dofs  OK
  112x224  50,850 dofs  SEGFAULT
  128x256  65,920 dofs  SEGFAULT

ROOT CAUSE: two BLAS libraries in one process. conda's libcholmod.5.dylib links Apple's Accelerate framework plus libomp (confirmed via otool -L), while numpy here is a PIP wheel bundling its own libopenblas64_.0.dylib in numpy/.dylibs/. CHOLMOD's SUPERNODAL factorization path calls BLAS; the SIMPLICIAL path does not. Supernodal only activates on larger matrices, which is exactly the observed threshold. Forcing mode='simplicial' via sksparse.cholmod.analyze(A, mode='simplicial') solves 128x256 cleanly (|u|max 1.06e6), which confirms the mechanism.

SECOND-ORDER HAZARD: CHOLMOD does not survive a caught factorization error. After a CholmodNotPositiveDefiniteError is raised and caught, the NEXT solve in the same process segfaults. Any retry/fallback logic must run in a fresh process or re-import, not a try/except around the existing solver.

TIMING (per factorize+solve, mean of 3):
  64x128   supernodal 56.2ms   simplicial 171.4ms   SuperLU 301.2ms
  96x192   supernodal 171.9ms  simplicial 622.9ms   SuperLU 849.1ms
  128x256  supernodal SEGV     simplicial 1734.7ms  SuperLU 1824.0ms

I HAVE TO CORRECT AN EARLIER CLAIM. In stage 0 I installed scikit-sparse and recorded that CHOLMOD roughly halves physics time. That was measured on small grids and does not generalize: at 128x256 the usable CHOLMOD mode (simplicial) is only 5% faster than SuperLU, and the fast mode segfaults. So the install bought a large win below ~37k dofs, no meaningful win at the target resolution, and a new silent crash. The .cursor/rules/environment.mdc line claiming CHOLMOD halves physics time needs the size qualifier.

OPTIONS, in order of preference:
1. Fix the BLAS conflict - reinstall suitesparse/scikit-sparse built against the same OpenBLAS numpy uses, or install numpy from conda so both use one BLAS. Restores supernodal everywhere; extrapolating the trend, ~500ms at 128x256, a ~3.5x win over the current best. Best long-term and directly serves stage 2 (iteration speed).
2. Size-gate the solver in _get_solver - supernodal below ~37k dofs, simplicial above. Cheap, safe, keeps the win where it exists, but leaves the target resolution slow.
3. Always simplicial. Simplest, gives up a 3x win on small grids.

Whatever is chosen, _get_solver must never be able to segfault the process silently.

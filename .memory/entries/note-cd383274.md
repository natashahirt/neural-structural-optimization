Found by adversarial review during stage 1, deferred by user decision because it is precisely the question stage 4 exists to answer rather than a defect in the stage-1 change.

THE DEFECT: with Heaviside projection enabled, physical_density(cone_filter=False) - the field train/base.py stores as ds.design and script/run.py save_final_designs_plot writes to disk - carries substantially more material than the volume constraint the objective enforced.

MEASURED, cantilever_beam_full 60x60, eta=0.5, RandomState(0)*2.0 logits, independently reproduced by the coordinator:
  volfrac=0.5 beta=16 -> objective 0.500000, render 0.500348 (+0.1%)
  volfrac=0.3 beta=4  -> objective 0.300000, render 0.359587 (+19.9%)
  volfrac=0.3 beta=16 -> objective 0.300000, render 0.411077 (+37.0%)
  volfrac=0.1 beta=16 -> objective 0.100000, render 0.291657 (+191.7%)

WHY IT WAS MISSED THE FIRST TIME, worth remembering as a methodological lesson: the fix was validated at volfrac == eta == 0.5, which is the SINGLE operating point where the Heaviside projection is mean-neutral, so the compensation is exactly zero and the error is invisible. Setting eta=volfrac shrinks the gap to -2.2%/+6.2%, confirming volfrac != eta is the driver. The shipped config runs volfrac=0.3 with eta=0.5. Any future validation of a projection-related change MUST be done off the volfrac==eta diagonal.

HOW IT AROSE: to keep default-path rendered output bit-identical for the Venice parity work, the engineer had render reuse the offset the objective solved rather than switching render to cone_filter=True. That preserved parity but replaced an exact property (mean(render) == volfrac exactly) with an approximate one.

WHY IT BELONGS IN STAGE 4: this is not really a bug in the reordering. It is two different density representations disagreeing, which is the exact subject of 'one canonical physical density shared by physics, CLIP, and output'. Resolving it here would pre-empt that design decision under time pressure.

SCOPE LIMIT: requires heavyside=True, which is opt-in and OFF by default. The default path is bit-for-bit unchanged and Venice parity is unaffected.

OPTIONS THE CRITIC PROPOSED: switch Environment.render to cone_filter=True (gating the change on projection being enabled, so the projection-off parity path is untouched); or solve a second offset for the render; or at minimum pin mean(render) against volfrac at volfrac=0.3 with beta in {4,16} so the number is visible.
